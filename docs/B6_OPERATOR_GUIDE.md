# B6 Admin and isolated QA guide

Use reviewed staging/synthetic accounts and published staging GameConfig. Do not create production test rewards, change prices/thresholds, activate real missions, migrate production or send live bot messages as part of development. Owner approval is required for operational rollout.

## Create the two real test missions through Admin

1. Give the operator normal view/add/change MissionDefinition and ClanMissionDefinition permissions plus `missions.activate_missiondefinition` and `clans.activate_clanmissiondefinition`. Published GameConfig lookup access is required. Superuser works in isolated QA; do not broadly grant production superuser.
2. Inspect the target ClanSeason's pinned published GameConfig. Its Clan policy must be enabled. Record its actual reward-band amounts; never copy demo numbers or enter arbitrary rewards. A definition using another version will not receive that ClanSeason's signals.
3. In **Clan mission definitions**, Add a Group draft: key `b6-group-activity`, version `1`, title/description appropriate to the existing Missions card, kind GROUP, requirement VALID_CLAN_ACTIVITY, a small explicit QA event target, chosen future/current start and end, the target ClanSeason published config and its GROUP reward band. Save. It remains disabled even if a crafted POST includes enabled.
4. Open **Preview / activate / deactivate**. Review config checksum, target, requirement, participant gross Points, direct HQ XP and Treasury split. Enter a reason, check confirmation and activate. Start/end timestamps use the timezone displayed by Django Admin; use explicit server UTC for QA records. No rewards are minted by preview or activation. Avoid a start earlier than intended: processed historical signals are not replayed.
5. Add an Individual draft: key `b6-individual-typing`, version `1`, kind INDIVIDUAL, requirement VALID_TYPING_RUN, target `1`, a published SMALL band and the same matching config. Add display text and valid window, save, review and activate as above. A successful eligible server-validated Typing run completes it automatically; Typing wallet claims remain separate.
6. For Group QA, have both Captain and Soldier contribute before the target is met. Only actual eligible participants receive Group participant payouts. Alternatively CLAN_CONTRIBUTION counts settled activity Contribution units, not raw characters or mission reward recursion.
7. Inspect read-only mission progress, participant, source events and signals in Admin; inspect Clan/player/Treasury ledgers and equipment APIs. The Mini App must display SETTLED automatically; there is no Clan mission claim button.
8. Deactivate with the same signed operation and a reason. Activation history and progress remain. Create a new version for changed kind, source, target, band, schedule or config; never edit committed history. New keys/versions are unique. Title/description may be corrected without economic mutation.

Personal missions: Add a disabled definition with an existing published policy key, supported verification family and matching repeat policy. Timed external requires a validated HTTP(S) destination; Telegram requires an integer nonzero telegram_chat_id and optional safe destination. Internal predicates remain server-owned (Season Brief evidence is still PH-043). Save, preview the effective policy/reward and activate explicitly. Verification, eligibility, repeat/reset, claim and integrations remain the existing services. A new economic reward requires a published GameConfig rule, not an Admin amount field.

## Treasury, Inventory and Missions QA

- In isolated PostgreSQL, use normal signed authenticated APIs and synthetic Telegram transports. Confirm no real bot token or production database is selected. Reuse the committed regression fixtures; no production credits.
- Record starting Player/Lifetime/Season, Treasury, Contribution, HQ XP/level and Clan Score. Ingest valid Telegram events through the webhook/worker test harness. Use the effective config's window and maximum exact/near-duplicate horizon: sample policy is 900 seconds plus its configured horizon, not a hardcoded worker assumption.
- Confirm a short valid zero-Gross window produces no reward/Treasury ledger. Then produce enough qualified characters for positive settlements and confirm Captain/Soldier attribution, `player+treasury=gross`, Contribution-before-split and existing HQ/Score accumulation. Reprocess/retry and confirm unchanged ledger counts/balances.
- At a reviewed 10% test rate, settle controlled Gross 2,1,4,3 via the test harness: Treasury credits 0,0,0,1; remainders 2000,3000,7000,0. Confirm audit metadata and canonical projection sums. Repeat with concurrent sources, deliberate rollback and separate published config versions. Never seed legacy remainders or production amounts.
- Exercise insufficient funds, Soldier purchase denial, allowed Captain purchase, idempotent purchase retry, quantity increase, explicit activation, quantity decrement, effect expiry and highest-per-category bonus. Treasury debit and purchase must commit together. Refresh equipment using server time; no client-triggered effect settlement.
- Confirm Group and Individual mission progress/completion/rewards; Group nonparticipants remain unpaid. Retry every source/task. Mission settlement cannot emit another contribution/activity signal. Recheck Recovery causes, suspended players, source-time access loss, closed-window/Season barriers and drain behavior.
- Compare HQ rank with Arena CLAN own_standing after projection consumption; lose Redis and confirm null/UNAVAILABLE, inject pending/stale projections and confirm RECONCILING, then rebuild and recover the same canonical standing.
- Test two distinct private `/start` updates, same-update redelivery, template change and delivery failure using synthetic transports only. Template activation creates no unsolicited Welcome. For JOIN/REJOIN, get credentials only through authenticated `/invite/current`, verify membership before ACTIVE, then exercise cancellation, revocation, expiry and uncertain/manual handling.

Run the full PostgreSQL suite plus `test_b6_*`, migration/drift/type/lint/schema/contract gates, the separate B2 benchmark and CI release/container scans. Device/WebView, frontend pinned contract acknowledgement and paired staging acceptance are separate evidence and remain pending until performed by FROCAL/owner.
