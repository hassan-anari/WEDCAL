## Authentication and compatibility

Use existing `Authorization: tma <initData>`. Every Clan read/mutation is private/no-store, varies by Authorization and resolves the Player server-side. Internal IDs are opaque application references, never Telegram identity assertions. Existing paths/fields remain. Added fields are additive; generic Clan errors now use the shared typed envelope:

`{code, detail, retryable, retry_after_seconds}`. Codes: `CLAN_FORBIDDEN` (403), `CLAN_NOT_FOUND` (404), `CLAN_STATE_CONFLICT` (409), `CLAN_RECREATION_BLOCKED` (409), `IDEMPOTENCY_CONFLICT` (409), `SEASON_UNAVAILABLE` (409), `REQUEST_INVALID` (422). ## P-11: governance and recovery

Existing `/leave`, `/governance`, `/removal-cases`, `/governance/{case_id}/vote`, `/dissolution`, `/recovery` remain authoritative. Governance reads include immutable electorate count, deadline, quorum/approval/minimum-voter rules, own eligibility/vote, and finalized counts/result. Votes remain one immutable ballot; repeated/conflicting casting follows the existing conflict response. Open-vote tallies are not exposed. Captain cannot instantly kick; target membership ID comes from the member-only roster.

Existing source-time access-loss/incidents, grace, inactivity warnings/removal, Captain recovery, bot-admin loss/restoration/deadline, timed dissolution and history preservation remain. Governance votes/finalization use ClanSeason-before-case locking to align with the existing recovery/economy lock order. Closed-Clan/ended-membership credential cleanup is bounded and durable through the existing periodic invite-recovery task: pending requests cancel; accepted/unsafe paths keep reservations until proven-safe revocation. No TTL or leave penalty is invented for accepted paths.

**PH-045:** the owner approved keeping same-Season Captain recreation blocked (owner decision in B5), returned as `CLAN_RECREATION_BLOCKED`; confirmed Captain Telegram authority loss enters `RECOVERY` with `CAPTAIN_AUTHORITY_LOSS`. Verified membership updates can enter recovery; only fresh `getChatMember` verification of the original Captain (`creator` or `administrator`) and the authorized bot can clear that cause. Activity alone cannot clear it. Independent inactivity/bot-loss causes and opened governance continue to block restoration. No new automatic dissolution, grace period, penalty, replacement Captain or recreation is introduced. Existing approved bot-admin-loss behavior is retained.

GET `/recovery` now adds `reasons`, `captain_authority_lost_at` and `can_verify_authority`; existing `reason` is the primary display cause. POST `/recovery/verify` is authenticated and original-Captain-only, returns the same schema, and uses shared Telegram API budgets. Unknown/failed verification returns the stable conflict envelope and never clears recovery. A bounded durable scan redrives lost-authority verification on the existing bot-admin worker cadence; fresh evidence is fenced against stale updates and concurrent results. Whole-second Telegram demotions tied with a precise verification conservatively pause at that verification boundary; precisely timed older API results cannot override newer evidence. Positive restoration is fenced against transitions committed during the remote calls. Notification `CLAN_CAPTAIN_AUTHORITY_LOST` commits through the existing Notification Center with the transition. Source-time activity/economic eligibility remains historical, so previously committed pre-loss obligations can settle without enabling new paused actions.

FROCAL must map the new reason/list to its existing RECOVERY surface. At audited FROCAL main, `ClanPage.tsx` derives recovery from the demo `supply-cache` effect and has no authority-loss lifecycle adapter or verification action. Map server state/reasons to the approved Recovery presentation, report missing representation and do not invent a new screen. ACTIVE/RECOVERY CLAN_HOME exclusively owns its group; no non-INACTIVE Creator registration may coexist; ending Clan never reactivates Creator state. No Captain succession or role-switch rule is added.

## P-12: HQ and economy

Existing `/home`, `/contributions`, `/treasury`, `/shop`, `/shop/{item_id}/purchase`, `/inventory`, `/inventory/{item_id}/activate` use canonical Phase 8 services/ledgers. No new reward engine, balance, refund currency or frontend settlement endpoint exists. A failed transaction creates neither debit nor purchase/use; a lost successful response is replayed with the same idempotency key. Never submit client balances or computed rewards.

New GET `/equipment` combines current versioned item rules (price, activation, duration, effects, owned quantity, use limit/count, purchase/use permission) and real active effects with server time. Highest bonus per category is effective; effects do not multiply player point rewards. Recovery, missing active Captain access, restricted player state, funds, inventory and capacity limits are enforced in services. Defence/Alliance/World Event catalog entries remain absent.

GET `/missions` exposes active and completed own-Clan mission definitions/progress, reward-band amounts, supported requirement availability, and own participant reward state/amount. Completion auto-settles through the existing mission engine; there is no invented claim button. Group completion does not imply every current member earned a participant payout.

Durable `ClanMissionSignal` adapts actual server-owned events into `record_mission_progress`:

- `VALID_CLAN_ACTIVITY`: one qualified, finalized Clan Home activity event.
- `CLAN_CONTRIBUTION`: contribution units from a settled Clan activity window (excludes mission rewards to prevent recursive rewards).
- `VALID_TYPING_RUN`: one server-validated eligible Typing run during a real Clan membership.

Only enabled, versioned definitions whose source-time window/config matches participate. No mission/threshold/reward is seeded from frontend demo cards. Unsupported requirement strings are explicitly UNAVAILABLE. Signal processing, participant rewards, direct HQ XP and completion commit together, using existing source/idempotency identities. Worker loss/retry cannot duplicate completion. Pending/poison signals remain visible in Admin and block season-close drain; retry attempt limits are operational configuration.

GET `/trophies` reads actual Clan-owned unlocks and canonical contribution/Treasury-earned targets. `banner-raised` is unavailable with `PH-048_PRODUCT_DECISION_REQUIRED`, null progress/target and no unlock/reward. There is no invented shared milestone. Existing Player First Clan/First Contribution remain separate Profile achievements.

## Administration

In-App announcements and Telegram Broadcast are distinct workflows sharing existing infrastructure. See [operator guide](B5_OPERATOR_GUIDE.md). Announcements never create Telegram deliveries. Multimedia Broadcast copies originals through `copyMessage`/`copyMessages`, preserves the B4 audience policy, and requires complete native preview before confirmation. Legacy text/API campaigns without a native source still use the existing sendMessage path.

Native campaign source is frozen by an atomic first-successful-preview reference. Bot-authored preview message IDs become the source for all subsequent previews and deliveries, so editing/deleting an original operator message cannot change confirmed content. Deleting the bot-authored source can make copying unavailable and is handled explicitly. Concurrent preview completions cannot replace the frozen source.
