# B6 independent review: Clan mission source-time activation

This supersedes the activation-state eligibility described at reviewed head `28a6b8805db5f9a8c70b78c5eadf5c6276dbccd1`. It stays within Draft PR #31. The owner approved a prospective observation cutover and holding uncertain earlier history, with separate approval required for any historical resolution. No production migration, replay or reward backfill has been performed.

## Confirmed defect and lifecycle

Production code required a change. The signal worker selected `enabled=True` at execution time, and the progress service independently rejected currently disabled definitions. Deactivation could discard eligible delayed work; activation could admit earlier work. The first-activation marker cannot represent inactive gaps or multiple cycles. For pre-existing definitions, migration 0017 stamped an observation rather than an original activation. Existing operator audit timestamps do not establish a complete, exact lifecycle for all definitions and direct database transitions. No historical intervals are inferred from either source.

The existing engine now checks the intersection of two half-open ranges against authoritative `signal.occurred_at`:

```
[active_interval.starts_at, active_interval.ends_at)
    intersect [definition.starts_at, definition.ends_at)
```

An open interval has no end. Exact activation and scheduled start are included. Exact deactivation and scheduled end are excluded. The current enabled flag remains the operator/UI state, but is not the test for delayed source eligibility. Reactivation opens a new interval; prior inactive gaps remain excluded. The pinned published GameConfig, source-time membership/access/context, moderation, Season economic window, finalization barrier and participant eligibility still apply. Group and Individual missions use the same existing automatic progress and settlement service; there is no claim action, new event source or separate reward engine.

PostgreSQL observes every definition enabled transition, including ORM bulk updates, in the same transaction. It uses `clock_timestamp()` after the definition row lock is held; transaction-start timestamps would be incorrect after a lock wait. Each interval has an immutable start/origin and can close once. PostgreSQL guards reject direct interval insertion/edit/deletion, enforce one open interval and an ordered end. A backwards lifecycle clock fails closed rather than creating overlapping intervals. Definitions retain immutable identity/economic semantics. A database-owned revision increments on every enabled transition; a signed preview from before a complete activation/deactivation cycle is stale even if enabled and first-activation fields look identical.

Admin retains permission, CSRF, actor-bound signed preview, expiry, reason and confirmation requirements. Preview lists source-time semantics, lifecycle revision and the unknown-history cutoff. The operation audit records interval ID, revision and the database effective timestamp. The interval model and source/progress/signal records are read-only in Admin. Title/description edits do not create intervals. Preview and activation do not settle rewards or send Telegram messages. Personal mission behavior is unchanged.

Workers select matching schedule/requirement/config definitions without filtering current enabled, lock them in primary-key order and recheck source eligibility under that lock. The progress service also locks the definition. Admin transitions take the same row lock through UPDATE, so eligibility, progress, participant assessment and settlement commit before or after a concurrent transition as one unit. The lock order is Season shared economic barrier, matching definition rows in primary-key order, per-source idempotency, ClanSeason, membership/participant accounting locks. The canonical settlement engine still owns player/Treasury conservation and all projections. No Treasury carry formula, GameConfig number, HQ threshold or item price changes here.

Committed source identities are checked before lifecycle reassessment. An identical replay returns the existing immutable progress rather than re-minting or being rejected merely because the definition is now disabled. Semantic conflicts still fail. A known inactive/out-of-window/ineligible source is terminal: the signal is processed without creating a source/progress/reward. Unexpected failures retain the existing bounded backoff/attempt budget and roll back sources, participants, ledgers, remainder and projections together. Unknown legacy history rolls back the entire signal transaction before holding it; no partial set of mission payouts commits.

## Migration 0019 and approved cutover

`clans.0019_b6_mission_active_intervals` adds:

- `ClanMissionActivation`: definition, database-observed start, optional end and origin (`STATE_TRANSITION` or `CUTOVER_OBSERVATION`), constraints/index/guards.
- Definition `activation_revision` and nullable `history_unknown_before`, both read-only/database-owned.
- Nullable `ClanMissionSourceEvent.activation`: populated for new progress, left null for historical committed sources.
- `ClanMissionSignal.requires_review`, initially false. Existing processed status, source identities, attempt budgets and events are not reset.

Within the atomic migration, a single database timestamp `C` is captured. Every pre-existing definition receives `history_unknown_before=C`. An enabled definition receives an open interval `[C, infinity)` with origin CUTOVER_OBSERVATION and revision 1; a disabled definition receives no interval and revision 0. This asserts only the enabled state observed at C, not historical activation. Existing `activated_at`, progress, source timestamps, participant outcomes, settlements, ledgers, balances and GameConfig remain unchanged. New definitions have no unknown-history cutoff and start with an empty known lifecycle until activation (or a database-observed interval if inserted enabled by an authorized backend process).

For an uncommitted signal earlier than C that matches a historical definition's schedule/requirement/pinned config, eligibility is unknown. The signal is held with `requires_review=true`, `error_category=activation_history_unknown`, `processed_at=null`. It receives no automatic retry or reward; attempts are not consumed. It remains visible in read-only Admin and continues to block the existing Clan mission Season-drain provider. A completed definition/source is preserved without re-assessment or duplicate credit. Already processed signals are never reopened. A signal at exactly C may progress against the enabled observation interval. Signals after C use only actual observed intervals.

**There is no review-release/replay button or automatic historical reconstruction.** Operators must report held signal IDs, matching definition versions, source times and available independent evidence for a separately owner-approved resolution. Merely clearing a hold or moving interval timestamps would be an unauthorized historical eligibility decision. A deployment is not ready to finalize a Season while these obligations remain unresolved.

The full rendered forward SQL is [B6_MISSION_LIFECYCLE.sql](evidence/B6_MISSION_LIFECYCLE.sql). Changes are additive; nullable source FK and constant signal default avoid rewriting economic histories. Definition metadata is initialized under the migration's schema locks; the definition table is expected to be small. ALTER TABLE/foreign-key validation still acquire locks on definitions, signals and source records: measure on staging with realistic table sizes and a deployment lock timeout. No non-atomic partial cutover is supported.

For an approved rollout, stop mission/economic writers and Admin mission changes, back up, apply the migration with the new image, verify interval/open-state consistency and held-work visibility, then start only the new mission workers. Never mix legacy workers that use current-enabled eligibility with the new lifecycle. The exact timestamp C is inspectable on definitions/observation intervals. Do not predate C to preserve apparent history.

**Rollback:** pause mission processing and Admin lifecycle changes; retain intervals, cutover markers, held signals and source links. Use a forward code fix that preserves source-time checks. Although a mechanical schema reverse exists for isolated migration testing, it drops activation evidence and is not a safe production rollback after transitions or progress exist. Returning to current-enabled filtering would reintroduce the defect. Do not delete holds, close the Season around them, replay rewards or downgrade/drop history without separate owner approval. Failed atomic migration rolls back its metadata and schema together.

## Regression coverage and consumer contract

`test_b6_mission_lifecycle.py` runs on real PostgreSQL and covers delayed Group/Individual completion, pre-activation rejection, inactive gaps through multiple cycles, exact activation/deactivation/schedule boundaries, participant eligibility, idempotent source/task retry, post-settlement failure rollback, stale signed preview after a full cycle, immutable interval guards, Season/recovery/finalization restrictions, pinned GameConfig identity and real reverse/forward migration cutover with preserved historical progress/settlement. Two concurrency tests assert actual `pg_blocking_pids` contention in both Admin-first and worker-first lock orders, then verify one settlement.

Older mission fixtures now choose controlled source timestamps at/after their database-observed activation rather than retroactively crediting events captured before mission creation. Existing economic/idempotency assertions are retained. Full-suite and CI results, exact runtime/schema revision and artifact head are published in the validation evidence and PR.

No HTTP response fields, endpoint paths or OpenAPI schemas change. Existing mission endpoints still describe currently displayed definitions and automatic settlement. A delayed settled achievement can appear after operator deactivation; its durable feed time remains the authoritative completion/source time, with the existing recorded-time semantics. FROCAL must acknowledge this behavior and re-pin the exact new WEDCAL revision in [coordination issue #8](https://github.com/hassan-anari/FROCAL/issues/8) and [frontend Draft PR #9](https://github.com/hassan-anari/FROCAL/pull/9) before implementation/paired tests. Existing paired evidence at the prior `28a6b880...` pin remains evidence for that revision only. No frontend code or approved UI behavior is changed here.
